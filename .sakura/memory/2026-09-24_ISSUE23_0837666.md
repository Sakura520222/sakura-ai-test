## 6. 经验教训与改进建议  

1. **标签体系细化**  
   - 为占位类 Issue 建立专用标签（`placeholder`、`test`）并在模板中提供选项，避免每次都靠 `invalid` 兜底。  
   - 在 `invalid` 与 `wontfix` 的使用边界上保留文档说明（如：`invalid` → 完全无需求，`wontfix` → 已确认的缺陷但不计划修复）。

2. **自动化过滤规则**  
   - 在仓库的 Issue Bot 中加入 **“单词/极短标题”** 检测，自动标记为 `placeholder` 并添加标准关闭注释。  
   - 对同一作者在短时间内创建的多个极简 Issue，直接归入 “测试/占位” 类别，减少人工审阅。

3. **重复检测策略**  
   - 引入 **时间窗口**（如 7 天）与 **相同作者** 过滤，提升对占位 Issue 的重复判定准确率。  
   - 使用 **标题相似度阈值**（如 Jaccard > 0.8）并结合 **描述关键词**，在极简情形下自动标记为 “可能重复”，但仍需人工确认。

4. **关闭流程标准化**  
   - 统一关闭时的注释模板，例如：`关闭原因：仅为测试占位 Issue，无实际需求。`  
   - 将该注释写入 **CONTRIBUTING** 或 **ISSUE_TEMPLATE**，让维护者一键使用。

5. **审计与清理**  
   - 每月执行一次 “low/invalid/placeholder” Issue 列表导出，检查是否有遗漏的业务需求或误判。  
   - 若发现长期未关闭的占位 Issue，主动与创建者确认后统一处理。

6. **对新手友好**  
   - 在 `ISSUE_TEMPLATE` 中加入 **“测试/演示”** 选项，引导新手在学习 GitHub 流程时使用专用模板，而不是直接创建普通 Issue。
